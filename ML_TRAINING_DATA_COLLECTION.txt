POSTURE CHECK - ML TRAINING DATA COLLECTION
============================================================

CURRENT STATUS
--------------
The TigerData schema has the current sensor-layout constraint. The collector
backend runs locally unless deployed. The Android app can upload only after a
cloud HTTPS collector and app build configuration are in place.


1. START THE COLLECTOR BACKEND
------------------------------
For local troubleshooting only, open PowerShell and run:

  cd "C:\Users\kalis\Downloads\SwampHacks 2026\SwampHacksXII-Posture-Check\cloudbackend"
  npm start

Leave this terminal open. The server listens on port 3000.

The backend's private cloudbackend\.env file contains TigerData connection
settings and COLLECTOR_API_KEY. It should also contain:

  DB_SSLMODE=require

Never share or commit this file. In require mode the database connection is
TLS-encrypted, but the server certificate is not verified; use this
development configuration only on a network you trust.


2. CHECK THE BACKEND-TO-DATABASE CONNECTION
-------------------------------------------
In a second PowerShell window, run:

  Invoke-RestMethod http://localhost:3000/health

Expected response:

  {"status":"ok"}

If this fails, check the terminal running npm start for the backend error.
Do not put TigerData credentials in the mobile app.


3. DEPLOY THE CLOUD COLLECTOR
-----------------------------
First run database/0004_streamed_captures.sql in TigerData's SQL Editor, after
the earlier schema migrations. Then create a Render Blueprint from this
repository using render.yaml. Set DB_HOST, DB_USER, and DB_PASSWORD from
TigerData when Render prompts; keep those secrets in Render only. The Blueprint
generates COLLECTOR_API_KEY. Render displays the collector's HTTPS onrender.com
URL after deployment. The free web service may sleep while idle; the first
health check or upload may take longer.


4. CONFIGURE THE ANDROID APP BUILD
----------------------------------
Set these variables in the EAS environment used by the development build:

  EXPO_PUBLIC_API_URL=https://<your-render-service>.onrender.com
  EXPO_PUBLIC_COLLECTOR_API_KEY=<same-value-as-render-COLLECTOR_API_KEY>

For local Expo development, put those same app variables in mobile/.env and
restart Expo. The app has no URL/token fields; tap Test backend to check the
configured cloud service. Never put TigerData credentials in EAS or the mobile
app. Rebuild and reinstall the Android APK after changing EAS environment values.

EXPO_PUBLIC_MODEL_API_URL is optional for collecting training data. It is used
by the live TCN assessment service, not by the collector.


5. CAPTURE LABELED TRAINING DATA
--------------------------------
1. Connect the physical shirt over Bluetooth.
2. Confirm all six physical sensors are reporting:
   - Flex type 1: IDs 0 and 1 (left and right elbow)
   - IMU type 2: IDs 0, 1, 2, and 3
3. Open Dev Testing, choose the correct posture label, and start a run.
4. Stop the run and save it with the selected good/bad label.

Valid Bluetooth samples upload to TigerData in ordered batches during capture.
Tap Save after stopping to finalize the run and attach its label; pending or
interrupted runs are excluded from training. Discard removes a pending run.
Demo/simulated readings are excluded. Keep the app open until the save
confirmation appears.
Current Runs are unlabeled and are not used for supervised training unless
they are labeled separately.


6. VERIFY THAT TIGERDATA RECEIVED THE RUN
-----------------------------------------
Run this in TigerData's SQL Editor:

  SELECT r.run_id, r.source, r.label, r.started_at,
         COUNT(s.sample_id) AS samples,
         COUNT(DISTINCT (s.sensor_type, s.sensor_id)) AS sensors
  FROM training_runs AS r
  JOIN training_samples AS s ON s.run_id = r.run_id
  WHERE r.status = 'complete'
  GROUP BY r.run_id, r.source, r.label, r.started_at
  ORDER BY r.started_at DESC
  LIMIT 10;

A complete capture should show sensors = 6. If fewer sensors appear, check
Bluetooth connection and sensor reporting, then make another capture.

Optional detail query to verify the sensor IDs in a run:

  SELECT sensor_type, sensor_id, COUNT(*) AS samples,
         MIN(captured_at) AS first_sample,
         MAX(captured_at) AS last_sample
  FROM training_samples
  WHERE run_id = '<run-id-from-query-above>'
  GROUP BY sensor_type, sensor_id
  ORDER BY sensor_type, sensor_id;

Expected new-layout IDs:
  type 1: IDs 0, 1
  type 2: IDs 0, 1, 2, 3


7. COLLECT ENOUGH DATA BEFORE TRAINING
--------------------------------------
The trainer requires at least 10 complete labeled runs per class:
10 good and 10 bad. These are only minimum run counts, not a guarantee of a
useful model. Collect substantially more varied examples across users,
movements, and sessions before relying on model results. Keep each Dev Testing
run consistently labeled; the current trainer applies one label to the whole
run.

After enough complete data has been collected, configure TigerData credentials
for the training environment and follow MachineLearning\README.md to train and
serve the TCN.
